      - human_id
      - ai_name
      - ai_language
      - last_active
      - god_mode

ITEM 3 — Update wrangler.toml (lines 76-89):

  [OK] Durable Object binding syntax is correct.

  [CORRECTION] Migration tag (line 85):
    The work order says:
      tag = "v2"
      new_classes = ["HumanAgent"]
      deleted_classes = ["ConversationRoom"]

    CLARIFICATION: If ConversationRoom was never deployed to
    production with a migration tag, you can't delete it in a
    migration. The deleted_classes directive only works for
    classes that were previously declared in a migration.
    If ConversationRoom was only in code (not in a migration),
    just remove it from the bindings — no deleted_classes needed.

    Also: if this is the FIRST migration, use tag = "v1",
    not "v2". Tags must be sequential from your first migration.

  [CRITICAL CORRECTION] Migration needs new_sqlite_classes:
    The work order says new_classes = ["HumanAgent"], but
    to enable per-agent SQLite (this.sql), the migration MUST
    use new_sqlite_classes instead:

      [[migrations]]
      tag = "v1"
      new_sqlite_classes = ["HumanAgent"]

    Without new_sqlite_classes, this.sql will not work and
    all SQL operations will fail silently or throw.

THINGS THE WORK ORDER GOT WRONG
================================================================

1. STATE BROADCASTING LEAK (CRITICAL)
   The work order puts conversation_history and personality_stack
   in agent state. setState() auto-broadcasts to all WebSocket
   clients. This would expose system prompts to the browser.
   FIX: Use agent SQL for conversations, private fields for
   personality stack. Only put UI-safe data in this.state.

2. MIGRATION TAG NUMBERING (MINOR)
   "v2" assumes there was a "v1". If this is the first migration,
   it should be "v1". Verify existing wrangler.toml migrations.

================================================================
THINGS THE WORK ORDER IS MISSING
================================================================

1. WEBSOCKET UPGRADE DETECTION
   No guidance on how the Worker detects and routes WebSocket
   upgrade requests to the HumanAgent. This is a critical routing
   step. (Cowork figured it out independently.)

2. AGENT SQL TABLE SETUP
   No mention of creating tables in onStart(). The agent's SQL
   database starts empty — you need CREATE TABLE IF NOT EXISTS
   for conversations, metadata, etc. (Cowork added this.)

3. THIS.BROADCAST() EXCLUSION
   The SDK's broadcast() takes an optional 'without' parameter
   to exclude specific connections. Useful for not echoing a
   user's own message back. The work order doesn't mention this.

4. CONNECTION TAGGING
   The SDK supports tagging connections (getConnectionTags) for
   targeted messaging. This would be useful for distinguishing
   web vs. native vs. God Mode connections.

5. VALIDATESTATECHANGE() HOOK
   The SDK has a validation hook that runs before state changes
   are persisted. Could be used for state integrity checks.

6. ERROR HANDLING STRATEGY
   No guidance on what happens when Claude API fails, Vectorize
   fails, or R2 is unavailable. The work order should specify
   fallback behavior for each failure mode.

7. DUAL STORAGE STRATEGY
   Cowork is storing messages in BOTH D1 (shared) and agent SQL
   (local). The work order doesn't address how to keep these in
   sync or which is the source of truth. This needs a decision.

8. AUTHENTICATION FOR NEW ENDPOINTS
   The work order adds /api/agent/:human_id/state and /history
   but doesn't mention authentication. Anyone who knows a
   human_id could read their conversation history.
